# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A headless data-ingestion bot for a movie/TV streaming-availability catalog. It has no app server and no UI — it's a collection of Python scripts that pull data from TMDB / OMDb, write to a Supabase (Postgres) database, and run on schedules via GitHub Actions. There is a separate Flutter app that reads from the same Supabase database, but it is not part of this repo.

## Commands

Tests: `python -m unittest discover -s tests -t .` (standard library, no pytest) and `python -m py_compile bot/*.py tests/*.py` — both run in Actions (the `tests` job of `nightly.yml`, on push and pull_request, without secrets). There is no linter or `pyproject.toml`. The gate for any change is those two commands with exit 0.

```bash
# Install dependencies
pip install -r requirements.txt

# The gates (run both before committing)
python -m py_compile bot/*.py tests/*.py
python -m unittest discover -s tests -t .

# Ingest scripts — HUMANS ONLY, ON PURPOSE. Every one of these writes to the
# production database. Claude Code must never run them; the Actions workflows do.
# (each script needs its own env vars — see below)
python -m bot.main
python -m bot.backfill_credits --role cast-order
python -m bot.bulk_import --batch-size 2000
```

**Known environment gotcha** (historical — it no longer reproduces under the current pin): `requirements.txt` pins `supabase==2.31.0`, with no lock file for transitive deps. Under the earlier pin, `supabase==2.9.1`, depending on when you `pip install`ed you could get a `realtime` version that needs `websockets>=13` while pip resolved an older `websockets==12.0` — which failed with `ModuleNotFoundError: No module named 'websockets.asyncio'` on `import supabase`; the fix was `pip install -U websockets`. With 2.31.0, `realtime 2.31.0` declares `websockets>=11,<16` and a fresh `pip install -r requirements.txt` resolves `websockets 15.0.1`. A local environment installed in the 2.9.1 era can still carry the old packages: `pip install -r requirements.txt` brings it in line with CI.

**Pillow** (`Pillow==12.3.0`, pinned in `requirements.txt`; the latest 12.x as of 2026-10 — 13.0 raises the Python floor to 3.11) is the repo's one image library: `bot/logo_luminance.py` decodes title logos with it. There is no numpy — the per-pixel loop over a w300 logo takes ~10–25 ms.

Every entry-point script requires env vars and **fails fast with a clear message** if one is missing (no silent partial runs):
```
[BOT] ERROR: Required environment variable 'TMDB_API_KEY' is not set.
```
A key that is set but refused fails fast too. On a 401 (since B5.5), `TmdbClient._get` and `TraktClient._request` print `[TMDB] ERROR: 401 Unauthorized for <url> — TMDb refused TMDB_API_KEY; stopping the run (exit 1).` (`[TRAKT] … TRAKT_CLIENT_ID` for Trakt) and `sys.exit(1)`. For TMDb that is the refused key. For Trakt it is not: Trakt's 401 is «OAuth must be provided», and on the public endpoints this bot calls an invalid client id or an unapproved app comes back as 403. So since B5.6 a 403 from Trakt ends the run too, with `[TRAKT] ERROR: 403 Forbidden for <url> — Trakt refused TRAKT_CLIENT_ID or the app; stopping the run (exit 1).` A TMDb 403 is still an ordinary client error. The run doesn't go on title by title through every caller's `except Exception` — Trakt Sync's Phase B drain included; Phase A's list fetches already raised out of `main()`. Any other 4xx still raises.

Required vars by script vary — `TMDB_API_KEY` + `SUPABASE_URL` + `SUPABASE_KEY` are needed almost everywhere; `OMDB_API_KEY` is only needed by `bot/main.py` and `bot/backfill_rt_scores.py` (Rotten Tomatoes scores). There is no `.env.example` — check the script's own `load_env()` function (always near the top) for its exact requirements before running it. `WATCHMODE_API_KEY` is **not used anywhere** — streaming data moved entirely to TMDB's `/watch/providers` endpoint; if you see a reference to it, it's stale.

## Architecture

### The four clients, one persistence layer

- `bot/tmdb.py` (`TmdbClient`) — all TMDB v3 API reads. One method per endpoint (`get_popular_movies`, `get_credits`, `get_watch_providers`, etc.), each returning plain dicts/lists so callers never touch raw API shapes. Has a shared `_get()` with retry/backoff baked in.
- `bot/omdb.py` (`OmdbClient`) — only used for Rotten Tomatoes scores (`get_rt_score`), via a multi-strategy title-matching fallback chain (IMDb ID → title+year → title → simplified title).
- `bot/trakt.py` (`TraktClient`) — Trakt API v2 reads for `bot/sync_trakt.py`: the watched/trending/anticipated lists (paginated through the `X-Pagination-Page-Count` header), `/search/tmdb/{id}` (`resolve_id`: our tmdb_id → Trakt's own id, the type as the filter), and `/related` by a Trakt id, a slug or an IMDB id. Paced at `TRAKT_RATE_LIMIT` (3.0/s), with the same retry policy as `TmdbClient`. Trakt sends this client no `X-Ratelimit` header (run #26: nine 429s, each a 300 s Retry-After, 60 % of the run asleep), so since B5.2 the client enforces its own sliding-window budget. Before every attempt, retries included, it waits until the oldest request leaves the window when the last `TRAKT_WINDOW_SECONDS` (default 300) already hold `TRAKT_WINDOW_CALLS` (default 420) of them; the 3.0/s bucket stays underneath as the burst cap. The first 429 of a run lowers that window to 75 % for the rest of the run (never below 100, nor above the configured value). A 429's Retry-After is read as seconds or as an HTTP date, bounded 1–300 s (anything else waits 2 s and says so). A 429 on a last attempt fails its title as before, but arms a pause the run's next request sleeps first, so it never leaves inside Trakt's penalty (B5.3). `sync_trakt.main` refuses a window under 1 call, or outside 1–600 s, before Phase A writes anything. Every 429 prints the requests and monotonic seconds since the previous one, its Retry-After and the response's header names (never other values), and the first response of a run prints its header names, once — the line that would show a limit header under another name. Error lines and raised errors carry no URL query string. The SUMMARY carries:
  - `trakt_budget` — as configured;
  - `trakt_budget_waits` — full-window waits of 1 s or more; the sub-second echo waits after the first window are slept but not counted;
  - `trakt_wall_calls` — the fewest requests up to a 429, counted from the start or from the previous 429; `-` when none came. A retry that meets a second 429 makes it 1, so read the per-429 lines then.
  - `trakt_limit` — `header-missing` when responses came and none carried `X-Ratelimit`; `unknown` before any response, or when the header only ever came malformed.

  B5.1's pause on the header (at `TRAKT_RATELIMIT_FLOOR`, 25, remaining or fewer, wait until `until`) is still there for a run that does receive the header.
- `bot/supabase_client.py` (`SupabaseClient`) — the only module that writes to the DB. Every other module treats it as an opaque persistence interface and never builds raw SQL. The expected schema is documented in its module docstring — **read that first** when touching any table shape.

### Pipeline stages (read in this order to understand the system)

1. **`bot/bulk_import.py`** — one-time/occasional catalog seeding. Hits ~40 different TMDB discover/genre/year endpoints, dedupes by `tmdb_id`, applies quality filters (language allowlist, tiered vote-count thresholds, runtime floor for movies), and inserts **bare** rows only — no credits/trailers/seasons/streaming. Enrichment is deliberately deferred to later stages. Run manually via the `Bulk Import` workflow.

2. **`bot/main.py`** — the nightly bot (`nightly.yml`, cron `0 6 * * *`). Numbered steps (1, 1b, 2, 2b, ... 17b) that:
   - Fetch ~12 TMDB list endpoints, dedupe (Step 7)
   - For genuinely new titles: fetch detail + watch providers + release dates, upsert (Step 9)
   - Re-verify streaming providers for existing titles due for a check (Step 10) — see staleness logic below
   - Refresh popularity scores and RT scores for the same due-for-recheck set (Steps 10b, 11, 11b)
   - Leave `is_in_theatres` alone: Step 13, which synced it from the now-playing list, is gone, and `daily_verify.py` (08:00 UTC) owns the flag. `backfill_states.py` writes `is_in_theatres = False` on every title it updates unless it gets `--skip-theatres`, and every workflow passes the flag since B4 (`tests/test_workflow_backfill_states.py` pins it), so no sequence empties the New in Theatres rail
   - Detect new seasons/episodes for `Returning Series` shows (Steps 14, 17, 17b)

   The step numbers have gaps (10, 14-16 were removed/replaced) — this is intentional history, not a bug; don't "fix" the numbering.

3. **`bot/enrich_new_titles.py`** — runs 3 hours after the nightly bot (`nightly_enrichment.yml`, cron `0 9 * * *`). Takes its queue from the server — `public.enrichment_queue(p_limit)`, migration `20261023170000`, through `fetch_queue()` — rows with `enriched_at IS NULL AND tmdb_missing_at IS NULL` in the order of what the app shows (in US theatres → inside a home-rail universe → by popularity → newest), and fails fast naming that migration if the function is missing; capped by `--limit=N` (the `=` form only): the scheduled run passes `--limit=1000`, a dispatch passes its own input (default 2000), `full_backfill_after_bulkimport.yml` passes `--limit=5000`; without the flag, the `ENRICH_LIMIT` env var, default 500, which no workflow sets; the server serves at most 5,000 rows, and PostgREST's max-rows setting caps any response — a title one run missed stays in the queue, served in that order. Per title it fills what Step 9 of the nightly never writes — the poster/carousel migration to Supabase Storage (`poster_url`), trailers, credits, seasons+episodes (TV) — and, only where Step 9 (or a bare insert) left them empty, the title logo with its luminance, the certification, the runtime (movies) and the genres. Its last step, States, always runs and writes only when `is_streamable_now` changes: true if ANY `streaming_availability` row exists (any region, rent/buy included — not Step 9's US-flatrate rule). It never writes `is_in_theatres`, which `daily_verify.py` owns — since B3.1; until then it set it to false (for titles with a provider row since `de25032`, on every write since `d396b4f`), evicting in-theatres titles from the New In Theatres rail until the next morning.

4. **Backfills** (`bot/backfill_*.py`, `migrate_images.py`) — one-off or periodic correction scripts, each scoped to a single field/table and each independently runnable. Two ways to trigger them:
   - `backfills.yml` — manual `workflow_dispatch` with a `job` dropdown (26 options, one job each), runs exactly one backfill.
   - `full_backfill_new.yml` / `full_backfill_update.yml` — two curated multi-step sequences, both `workflow_dispatch`-only (not scheduled). **The split is deliberate**: `_new` chains backfills that only touch rows where a field `IS NULL` (images → trailers → credits → seasons → title-logos → title-logo-luminance → backdrops → certifications → runtime → genres → metadata → states, then `cleanup_short_films` and a closing `summary` that runs even when a step failed); `_update` chains backfills that unconditionally refresh already-populated data (popularity → popularity-score → vote-count → status → tmdb-scores → season-ratings → rt-scores → imdb-ids → streaming → release-dates). If you add a new backfill script, decide which bucket it belongs in before wiring it into either workflow.

   **Title logo luminance.** `bot/backfill_title_logo_luminance.py` (`backfills.yml` job `title-logo-luminance`; step 5b of `full_backfill_new.yml`, in the `_new` bucket because it only touches rows where `title_logo_luminance IS NULL`) measures every logo that has a `title_logo_url` but no luminance yet. It is re-runnable by construction: one dispatch may not get through the catalogue, so it stops itself after 170 minutes (inside the Backfills job's 180) and its last line says how many logos are still NULL — dispatch again while that is more than the run's `unmeasurable`. In `full_backfill_new.yml` it shares that job's 240 minutes with every other step, so drain the backlog from the Backfills job first. The number has ONE definition, `bot/logo_luminance.py`: Rec. 709 relative luminance over linearised sRGB, composited over black, averaged over the visible pixels; an SVG answers 1.0; `NULL` means not measured, never 0. Every writer of `title_logo_url` writes it in the same payload — enrichment Step 5, `backfill_title_logos.py`, the nightly's Step 9 (`step9_logo_fields()` in `bot/main.py`, through `upsert_media`, which always writes both keys from its dict) and, since B4, `backfill_dark_logos.py` — so a row is NULL when its logo could not be measured at write time, or was written before the column existed (migration `20261022193500`, the backlog this backfill drains), and it stays NULL until the next dispatch of this backfill: a failed measurement does not correct itself.

   **Title logo choice.** Which logo a title gets has ONE rule too, `logo_luminance.choose_logo`, and every writer of `title_logo_url` reaches it through `TmdbClient.choose_title_logo` (B4; until then `get_title_logo` kept the first English logo TMDb lists, and for popular titles that first one is often a dark variant while a light one exists — 4,495 logos were under the line on 28/10). The pool is `title_logo_candidates`: the English logos in TMDb's order, or every logo when there is none. The line is `MIN_LOGO_LUMINANCE`, 0.10: the app's `kTitleLogoMinLuminance` (`lib/features/detail/presentation/screens/detail_screen.dart`, the row 7 rule), at or above which the detail screen draws the logo and under which it draws the text title; the bot's line moves with the app's, in the same commit as the app's change. The first candidate is measured; at or above the line, or unmeasurable, it wins as before (one fetch, the same answer). A known-dark first one sends the walk on, in TMDb's order: the first measured at or above the line wins; an unmeasurable one is passed over (a known-dark logo shows the text title, an unknown one could be an invisible logo), and three unmeasurable in a row end the walk (the CDN is failing); if nothing wins, the lightest measured does, TMDb's order breaking a tie, so the first stays when nothing is lighter. The winner comes back with its luminance, so the writer writes both keys in one payload and no URL is fetched twice. `bot/backfill_dark_logos.py` (`backfills.yml` job `dark-logos`; in neither full sequence, since it corrects populated rows once) gives the rows already under the line (`title_logo_luminance < MIN_LOGO_LUMINANCE`; a NULL is never touched) the chooser's logo when it is a different URL with a measured luminance higher than the stored one: one update with both keys and one line per change (the title, the old URL and luminance, the new ones), then a summary (`checked`, `to_light`, `to_lighter`, `nothing_lighter`, `no_logos`, `errors`, `still_dark`). It stops starting rows at 170 minutes, and a row where every logo TMDb offers is dark stays under the line for the next dispatch. Dispatch it once now, and again whenever the app's line moves. TMDb Mirror runs after Backfills, so the new logos reach our Storage by themselves.

5. **`bot/cleanup_low_quality.py`** — the monthly cleanup, **disabled since 2026-08-05**. It had been deleting titles that user data (reviews, watchlists, favorites and so on) references with ON DELETE CASCADE. `nightly.yml`'s monthly cron (`0 6 1 * *`) is commented out, its `monthly-cleanup` job is `if: false`, and no other workflow runs the script. The workflow's comment asks for the user-anchored guard to be verified before either goes back on; that is a decision, not a fix.
   - Without `--apply` the script is a dry run (the disabled job passes it).
   - It first skips every user-anchored title: a `media.id` in any of the twelve `PROTECTED_SOURCES` table/column pairs.
   - It never deletes a title that is streamable, in theatres, released in the last 90 days, or released in the last 2 years with a rent/buy row.
   - It deletes any other title with no poster, or with fewer votes than its release year's tier: 500 from 2019, 700 for 2010–2018, 1,000 before that.
   - A second pass deletes movies under 40 minutes that are not in theatres, not streamable and not user-anchored.

   (`bot/cleanup_short_films.py`, step `cleanup_short_films` of `full_backfill_new.yml`, is a separate script.)

6. **`bot/sync_trakt.py`** — Trakt Sync (`trakt_sync.yml`). It writes two things the app reads.
   - **The `trakt_*` columns.** `get_trending_this_week` (Home's Trending This Week rail and the hero banner) orders by `trakt_watchers_week`. `get_media_popular` blends a `trakt_watchers_week` rank 50/50 with its score. `get_new_in_theatres` admits a title on `trakt_watchers_week >= 500`, one of its three quality gates (the others are 50 votes and popularity 50). `get_coming_soon` admits on `trakt_anticipated_score >= 1000` (or popularity ≥ 20) and breaks ties with it. The cards draw a heat badge at `trakt_watchers_week >= 2000`, and the detail screen's «N watching» is gated by `trakt_trending_rank` and prints `trakt_watchers_week`. Only the bot's own `compute_popularity_score` ignores them. (The module called itself «shadow mode» until B5.1; the label was older than these readers.)
   - **`media_related`.** The app's More Like This rail reads it through `get_related_titles`.

   Phase A ingests Trakt's watched/trending/anticipated lists, then decays the heat of titles that fell off every list through `public.trakt_decay_heat(p_before, p_limit)` (migration `20261025160000`): 200 rows a call while a call returns 200, at most 50 calls, and it prints `decayed heat on N title(s) in K call(s)`. Until B5.1 it was one UPDATE over every row ever stamped, which hit PostgREST's 8 s statement timeout on every run and left stale heat on the Trending rail.

   Phase B drains related titles. Since B5 (decision 1.439), Phase B takes its queue from the server: `public.trakt_related_queue(p_limit, p_before)`, migration `20261024210000`, recreated by `20261025160000`, through `get_titles_for_related_drain()`. The queue holds titles with `tmdb_missing_at IS NULL` that were never synced or were synced before `TRAKT_RELATED_FIX_DATE` (`2026-10-24T16:00:00Z`; every older stamp came from the wrong path). It serves them in the app's order (in US theatres → inside a home-rail universe → by popularity → newest), with each row's `imdb_id`. Since `20261025160000` a partial index holds the pending set in that order, so a slice takes milliseconds; B5's seq scan and sort took 2.5 s alone and crossed the 8 s timeout under the other jobs' load (`57014`, now retried like a 503). Phase B asks in slices of 1,000 (PostgREST's cap) until `TRAKT_RELATED_BATCH` is filled or a slice comes back short.

   Per title, it asks `/related` by the title's IMDB id when the row carries a well-formed one (`^tt\d+$`): one Trakt call. Otherwise, or when Trakt answers 404 for that IMDB id, it resolves Trakt's own id (`TraktClient.resolve_id`, `/search/tmdb/{id}?type=movie|show`) and asks `/related` by THAT id. The SUMMARY counts `related_by_imdb` and `related_by_tmdb`. Before B5 it passed our `tmdb_id`, which Trakt read as its own id: most titles got nothing, and the rest got another title's relateds. Each title is then ONE write, `public.trakt_replace_related(p_media_id, p_rows, p_synced_at)` through `write_related()`: its `media_related` rows replaced and its stamp written in one transaction, zero rows for a title Trakt does not know. It used to be a DELETE, an INSERT and a PATCH, and the stamp could land without its rows.

   The guards:
   - The run refuses to start at or before the fix date, before Phase A writes anything.
   - A missing server function exits 1, naming its migration: the queue's `20261024210000`, or `20261025160000` for the write and the decay. Nothing is stamped after that. For the queue and the write, Phase A's writes have already landed by then.
   - Phase B exits 1, after the SUMMARY, when a queue slice fails for good (after the retries), keeping what landed.
   - Phase B exits 1, after the SUMMARY, when the stamps are not landing: a full slice brings nothing the run has not tried and some of it was stamped, or a title comes back after its second stamp. One lost stamp, or a short slice of them, is drained once more. A title whose drain failed was never stamped, and heads the next slice as an error.
   - The time budget (`TRAKT_TIME_BUDGET_MIN`, default 80, inside the job's 100 since B5.6, 90 before) stops the drain before the next title or slice. It prints the SUMMARY and exits 0: a plan, not a failure. The job's margin is 80 + one 5-minute budget window + two Retry-After at 300 s (one request's retries) + ≈ 3 minutes of setup before the budget's clock starts = 98; `test_the_budget_ends_inside_the_jobs_timeout` checks that sum, from the code's constants and a 3-minute setup allowance, against the workflow's `timeout-minutes`. It is one request's worst case, not a title's: a title in flight makes up to three Trakt requests, so one that met two 429s on each could still run past 100.

   Cadence: daily at 02:17 UTC, off the top of the hour that GitHub delays (the 03:00 run of 25/10 started five hours late). Each run takes up to 5,000 titles (3,000 until B5.4) and a budget of 80 minutes, while the backlog is re-drained; then back to Mondays. On 26/10 the server counted 123,962 titles pending: ≈ 25 days at 5,000, a floor because a failed attempt counts against the 5,000, new titles keep arriving and the time budget can end a run first. A title costs one database write and one Trakt call by IMDB id, two when it is resolved first, three when Trakt answers 404 for its IMDB id (`related_by_tmdb` counts those too). Run #29 (26/10) drained 3,000 in 58 min with no 429: 1,283 by IMDB id, 1,717 by lookup, ≈ 4,700 requests (≈ 1.57 a title), with the budget's 51 waits the only brake. The 80 minutes hold ≈ 6,700 requests at 420 per 300 s, so 5,000 titles fit at up to ≈ 1.3 requests a title. `bot/backfill_imdb_ids.py`, as it stamped IMDb ids, brought the head under that. Run #30 (27/10) stamped the full 5,000 in 62 minutes with no budget cut: at most ≈ 1.1 requests a title, since 62 minutes hold at most ≈ 5,400 requests at that budget. Should the cost climb back over ≈ 1.3, the time budget stops the drain short of 5,000: the line `time budget of 80 min reached after N title(s)`, then the SUMMARY with `related_scanned=N`, exit 0 — a plan, not a failure. A 429 (#26's came as few as ≈ 330 requests apart) still costs its 300 s Retry-After and lowers the window to 315 per 300 s for the rest of the run, so that run ends shorter, the same way. Go back by hand once no row with `tmdb_missing_at IS NULL` has `trakt_related_synced_at` before the fix date. A title that fails every attempt keeps its old stamp, so if that check stalls on a handful of rows that `related_errors` keeps counting, look at them rather than waiting. `tests/test_workflow_trakt_sync.py` pins the daily cron, the batch, the time budget, `window_calls` and the workflow's header, so they change in the same commit; the workflow's top comment says the same.

7. **`bot/posters_hd.py`** — Posters HD (`posters_hd.yml`), since B5.7. It makes an HD copy of the poster of every title that can reach the app's slideshow, so the app reads one more column instead of calling TMDb (decided 27/10): the slideshow crops a 2:3 poster to 9:16 for a 1080×1920 card, which needs at least 1280×1920 of poster, and `poster_url` is our Storage copy of TMDb's w500. The set is every distinct `media_id` of `media_list_items` plus every non-null `media_lists.cover_media_id`, read in keyset pages by `id`, then those `media` rows by `id` in chunks of 100; a row with `tmdb_missing_at` set is left out, and one with no `poster_path` is skipped. A title is pending while `poster_hd_url` is null or its file's stem differs from `poster_path`'s (TMDb changed the poster; any `?…` query is ignored on both sides). The source is TMDb's original (`/t/p/original/<file>` from `poster_path`, never from `poster_url`), fit inside 1280×1920 as a JPEG, quality 85, progressive; a JPEG that already fits goes up byte for byte, and nothing is upscaled. It lands at `media-images/posters-hd/{tmdb_id}/{stem}.jpg`, and its URL goes to `media.poster_hd_url` (migration `20261027200000`; null means not made yet, and the app falls back to `poster_url`) in one PATCH by `id`. It never writes `poster_url` or `poster_path`, and never deletes a file: an HD file whose title leaves every list stays, and so does the old one after TMDb changes the poster, so the folder only grows. The image CDN needs no key: the job's only secrets are `SUPABASE_URL` and `SUPABASE_KEY`. Cadence: hourly, so a title added to a list gets its HD poster at the next run once the backlog fits in one batch; at :41, off the top of the hour that GitHub delays (the reason Trakt Sync runs at 02:17); plus dispatch. An hour with nothing pending ends in seconds with `pending=0`. A batch of titles attempted (`POSTERS_HD_BATCH`, 300; a 404 or an error counts and stays pending) and a time budget (`POSTERS_HD_TIME_BUDGET_MIN`, 20, inside the job's 30) end a run with `[POSTER_HD] SUMMARY …`; a missing column fails fast at the read of the media rows, naming the migration. Since B5.8 its uploads carry a one-year cache: `upload_image`'s optional `cache_seconds`, which storage3 sends as the multipart `cacheControl` field the server stores; without it the server stores `no-cache`, as for migrate_images', the enrichment's and backfill_seasons' uploads. A dispatch with `refresh_existing` 'true' makes every made poster still in the set pending again, so the ones made before that cache are uploaded once more with it; their URLs do not change, so nothing is written. A refresh is bounded by the batch and the time budget like any run, in `id` order (a set larger than one batch needs the `batch` input raised to cover it), and one that fails is not retried by the hourly runs. It belongs to neither `full_backfill_new` nor `full_backfill_update`: it has its own schedule.

8. **`bot/tmdb_mirror.py`** — TMDb Mirror (`tmdb_mirror.yml`), since B5.8. It copies every image the app still loaded from `image.tmdb.org` to our own Storage, so the app reads everything from our side (decided 27/10): backdrops at `w1280` (from `media.backdrop_path`), title logos at `w500` (from `media.title_logo_url` when its size segment is `w500`; any other is counted `skipped_size` and never fetched) and cast and crew photos at `w185` (from `media_credits.profile_path`). Each file lands at `media-images/tmdb/{size}/{file}` under TMDb's own file name — the app builds our address from the path it already has — byte for byte as TMDb served it (never re-encoded or resized), with the content type the CDN answered (JPEG, PNG, SVG or WebP; anything else is an error) and a one-year cache, since a TMDb file name never changes its bytes. A ledger remembers each file once, `ok` with its byte count or `missing` for a 404, so a 404 is not asked every hour: `public.tmdb_image_mirror`, primary key `(size, file)`, read through `tmdb_mirror_titles(p_after, p_limit)` (titles in `id` order with `tmdb_missing_at` null, each with the distinct `profile_path` of its credits) and `tmdb_mirror_missing(p_size, p_files)` (which of up to 1000 files the ledger does not hold). All three come from migration `tmdb_image_mirror`, which is Claude's; without it the script stops at its first call, naming it. The sweep is stateless: every run walks the catalogue from its first page (200 titles, keyset by the last `id`), asks the ledger per size in chunks of 1000 (about 5 calls a page), copies what is new with a pool of workers (`TMDB_MIRROR_WORKERS`, 6, 1–16; one Supabase client per worker thread; the RPCs and the ledger stay on the main thread), and upserts the page's ledger rows (on `size,file`, 500 a call) after the page's uploads — a run that dies in between uploads those files again next time, harmlessly. An error (a timeout, a 5xx, a content type it does not keep, a failed upload) records nothing and is asked again next run; a file name the ledger cannot hold (5–120 characters, no '/' or '?') is an error on every run and never fetched; 50 failed files in a row stop the run red, since the CDN or Storage is down. Every RPC and ledger write gets the house's retry of transient failures (3 attempts, 2 s then 4 s); one that still fails stops the run with what landed, its line and the SUMMARY, exit 1. It reads `media` and `media_credits` only through its RPC and never writes them; it never deletes a file or a ledger row. Cadence, since B5.9 (hourly at :11 until the first copy completed on 28/10): a sweep with nothing new still costs ≈ 3,300 calls and ≈ 50 MB of database egress (≈ 7 minutes) and ends with `copied=0`, so it runs only when an image can be new — after each workflow that writes one (Nightly Bot, Nightly Enrichment, Backfills, Full Backfill — New Data and Full Backfill — After Bulk Import) through `workflow_run` with `types: [completed]`, since a failed run may still leave rows to mirror (an upstream run started by a push or a pull request, which runs only the tests, starts no sweep); once a day at 12:23 UTC as a fallback, off the top of the hour and after the nightly chain, so a dropped event or a skipped cron costs at most a day; and on dispatch. `tests/test_workflow_tmdb_mirror.py` derives that list from the workflows that run an image writer, so a new one joins it in the same commit. A time budget (`TMDB_MIRROR_TIME_BUDGET_MIN`, 25, 1–80; a dispatch may ask up to 80 while the first copy drains — nominally 80 plus the last chunk in flight, 4 files a worker at a fetch and an upload timeout each, plus setup, ≈ 86 of the job's 90; timeouts are per phase and the page's ledger write after that chunk is not counted) and a file cap (`TMDB_MIRROR_MAX_FILES`, 20,000, counting every file attempted: copied, missing or an error) end a run with `[TMDB_MIRROR] SUMMARY …` (`sweep_done=1` when it reached the last page inside the budget); the next run continues where the ledger says. A knob outside its range is refused before any work. Its only secrets are `SUPABASE_URL` and `SUPABASE_KEY`. It belongs to neither `full_backfill_new` nor `full_backfill_update`: it has its own schedule.

### Conventions that span files

- **`load_env()` fail-fast pattern**: every script's `main()` starts by calling a local `load_env()` that checks `os.environ` for its required keys and `sys.exit(1)`s with a labeled error if any are missing. Copy this pattern exactly when adding a new script — don't introduce `python-dotenv` loading or default-fallback behavior.
- **Upsert conflict keys** are load-bearing and table-specific — get them wrong and you silently duplicate rows instead of updating:
  - `media`: `tmdb_id`
  - `media_seasons`: `(media_id, season_number)`
  - `media_episodes`: `(season_id, episode_number)`
  - `media_credits`: `(media_id, name, role)`
  - `media_trailers`: `(media_id, youtube_key)`
  - `streaming_availability`: `(media_id, provider_name, region, monetization_type)`
- **One row per TMDb number, whatever the type**: `media` is `UNIQUE (tmdb_id)`, but TMDb numbers movies and shows in separate sequences, so a show and a movie can share a number and the catalog holds only one of them. A writer that matches a TMDb or Trakt candidate to a stored row by number must compare `media_type` first and skip a mismatch. Three places already do: `sync_trakt.py` Phase A (`type_mismatches`), `sync_changes.py`'s refresh (`type_mismatches`), and since B5.5 the nightly's Step 8b, whose SUMMARY counts `dedup_cross_type` (Step 7 dropped the other type), `skipped_other_type` (Step 8 skipped a candidate stored as the other type) and `cross_type_collisions` (Step 8b would have written that poster).
- **PostgREST `order` column gotcha**: `media_credits.order` can't be filtered via the normal `.eq()`/`.is_()` query-param style, because PostgREST reserves the `order` query parameter for sort directives — `?order=is.null` gets parsed as a (broken) sort clause, not a filter. See `fetch_cast_order_targets()` in `bot/backfill_credits.py` for the workaround (fetch role='cast' rows, filter for `order IS NULL` in Python).
- **`ALLOWED_PROVIDERS`** (`bot/supabase_client.py`) is the single source of truth for which streaming platforms get persisted — TMDB's `/watch/providers` returns far more (regional/niche) services than the catalog wants. `get_watch_providers()` in `tmdb.py` returns the raw `{flatrate, rent, buy}` dict; callers (`main.py`, `backfill_streaming.py`) filter each list through `ALLOWED_PROVIDERS` before upserting. `is_streamable_now` is derived from `flatrate` only — rent/buy availability doesn't count as "streamable."
- **`streaming_availability.first_seen_at`** is intentionally omitted from upsert payloads so its DB-level `DEFAULT now()` only fires on true INSERT; it's never touched on conflict/UPDATE, so it always reflects when a title first appeared on a platform.
- **`compute_popularity_score()`** (`bot/supabase_client.py`) is the one piece of non-trivial business logic in the codebase, shared by `upsert_media()`, `backfill_popularity_score.py`, and the nightly bot's Step 10b. Bayesian-weighted blend of normalized popularity (30%), TMDB score (65%, or 70% if `rt_score` is `None` — its 5% weight gets redistributed rather than treating missing as zero), and RT score (5%), shrunk toward a global mean (`_BAYES_C = 72.07`) based on vote count (`_BAYES_M = 500`), then scaled by a tiered freshness multiplier: 0 if no `release_date`, vote-scaled (full boost at 200+ votes) if ≤30 days old, exponential decay (vote-scaled, full boost at 100+ votes) beyond that. Read the function before changing any weight — it's been tuned iteratively and the tiers are not symmetric by accident.
- **`get_titles_to_reverify()`** (`bot/supabase_client.py`) drives Step 10/10b/11's "who gets rechecked today" — 8 overlapping, deduped buckets keyed on `streaming_last_checked` staleness (3/7/30/90 days depending on category: coming soon, in-theatres recent/old, streamable, old titles, and three TV-specific age bands). If you change re-check cadence, this is the one function to touch — don't add ad-hoc date math in `main.py`.
- **`_PRE_RELEASE_STATUSES`** (`In Production`, `Post Production`, `Planned`, `Rumored`) gates OMDb/RT lookups — there's no point querying Rotten Tomatoes for a movie that hasn't released. Checked in `upsert_media()` and the Step 11 movie filter in `main.py`.
